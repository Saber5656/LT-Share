# LT Share on X 要件定義書

> **2026-10-20 要件変更:** 利用者の「フロントで軽量モデルを起動してもよい」「実装してみて」に基づき、端末内LLMを初期実装の対象に追加する。以下のv1.0のC-04・FR-05・対象外にある「本人のChatGPT利用枠のみ」「端末内LLMは対象外」は今回の試験版には適用しない。Sitesの単独Web、独自DBなし、写真・投稿案の端末内保持を維持する。モデル初回ダウンロードと対応GPUを必要とし、非対応・失敗時は手入力へ戻る。写真ライブラリへの直接保存という既存要件は緩和せず、未達として残す。[最新の実装・検証状態](verification.md)を参照。


- 文書ID: LT-SRS-001 / Version 1.0 / 作成日: 2026-10-09
- 状態: 要件整理済み。技術的な成立性・実機動作は未検証。

OpenAI Sitesを利用し、本人のChatGPT利用枠で文章を生成する。写真・動画・投稿案は利用者の端末へ保存し、独自バックエンド・サーバーDBは設けない。最終投稿はX上で利用者が行う。

> 本書は要件定義書であり、実装済み・検証済み・公開済みを示すものではありません。

## 1. 目的・対象範囲・構成の前提

### 1.1 解決する課題

短いLTが連続する開発系イベントでは、撮影、要約、ハッシュタグ入力、登壇者の確認、Xへの投稿を毎回手作業で行うと、次の発表を聞く時間が失われる。本プロダクトは、記録から投稿準備までの操作を減らし、聴講を妨げずに共有できる状態を作る。

対象はLuma、connpassなどで案内されるイベントを含む開発系イベントの参加者。これらのイベントサービスとのAPI連携は初期版に含めない。主な利用端末はスマートフォンとし、具体的なOS・ブラウザの対応範囲は実機検証で確定する。

### 1.2 初期版の対象／対象外

| 区分 | 内容 |
| --- | --- |
| 対象 | ハッシュタグ設定・引き継ぎ、写真／動画の記録と端末保存、AIによる100文字程度の文章生成、任意の開発者ラベル、Xでの確認・投稿への誘導、前回の投稿案保存。 |
| 対象外 | X APIによるアカウント検索・直接投稿、登壇者一覧の事前登録必須化、投稿結果の自動取得、独自会員管理、クラウド履歴同期、運営者負担のAI API、端末内LLM。 |
| 将来 | モバイルアプリ化、広告、サブスクリプション。初期版への実装や価格・プラン内容は確定していない。 |

### 1.3 変更しない構成上の前提

| ID | 前提・制約 |
| --- | --- |
| C-01 | OpenAIのSites上での起動・提供を前提とする。端末保存などの要件を満たせる場合はWebアプリを採用する。 |
| C-02 | 本プロダクト専用のバックエンド、独自APIサーバー、サーバーレス処理、サーバーDB、クラウドファイル保管基盤を新設しない。 |
| C-03 | 「永続保存なし」は独自のサーバー側保存基盤を設けない意味とする。写真・動画・投稿案・ハッシュタグの端末内保存は許容する。 |
| C-04 | AIは利用者自身のChatGPT利用枠でOpenAIの軽量モデルを実行する。モデル名と利用可能プランは検証後に確定する。 |
| C-05 | 独自の認証情報保管・会員DBは作らない。必要な本人確認・利用許可はOpenAIの公式方式に従い、XへのログインはX側で行う。 |

**境界の定義**: 「フロントのみ」は、アプリ固有の処理・状態管理を端末側で行う方針である。Sitesのホスティングや公式認証、OpenAIのモデル実行、Xでの投稿まで端末内に閉じるという意味ではない。C-01〜C-05を同時に満たす接続方式はG-01で検証する。

## 2. 利用フロー・画面要件

### 2.1 基本フロー

| 段階 | 利用者の操作とシステムの動作 |
| --- | --- |
| 準備 | Sites上のLT Share on Xを開く。必要なOpenAIの利用許可を行い、イベントハッシュタグを設定する。登壇者の事前登録は不要。 |
| 記録 | 「記録する」を押し、写真または動画を撮影する。撮影データを取り込み、端末への保存を行う。 |
| 投稿準備 | 利用可能な記録内容から100文字程度の投稿文を生成する。必要な場合だけ「開発者をポストに含める」を有効にする。 |
| 確認・共有 | 「ポスト確認」からXへ移動する。本文を確認し、必要なら「開発者：」の後に@入力で追記する。自動添付できないメディアは端末から添付する。 |
| 次のLT | LT Shareへ戻り「次の投稿へ」を押す。前回の投稿案を保存し、ハッシュタグだけを引き継いだ新しい投稿を開始する。 |

Xへの投稿を保留して先に次の記録へ進める。Xへの遷移や「次の投稿へ」の操作を、X上の投稿完了の証拠として扱わない。

### 2.2 必須の画面要素

| 要素 | 要件 |
| --- | --- |
| プロダクト名 | 「LT Share on X」と表示する。 |
| ハッシュタグ欄 | 設定中のハッシュタグを確認・編集できる。次の投稿でも保持する。 |
| 記録する | 写真／動画を記録する入口。端末に応じた撮影UIを利用する。 |
| 記録メディア・状態 | 対象メディアと保存／文章生成の状態を識別できる。アプリ内表示と端末への保存完了を混同しない。 |
| 生成文章 | Xに渡す文章を確認できる。本文の編集方法は画面設計で具体化する。最終修正はX上でも行う。 |
| 開発者をポストに含める | 有効時のみ「開発者：」を本文に追加するトグル。登壇者の指定を必須にしない。 |
| ポスト確認 | 投稿本文と、対応する場合はメディアをXの投稿用UIに渡す。 |
| 次の投稿へ | ヘッダーまたはフッターに配置する。「ポスト確認」の下は配置候補であり、固定レイアウトではない。 |
| 保存済み投稿案への導線 | 保存した前回の投稿案を再確認できる。履歴一覧の見せ方は詳細設計で決める。 |

**UIの確定範囲**: 本書は画面の役割と必須操作を定める。配色、ワイヤーフレーム、トグルの初期値・次回への引き継ぎ、細かなレイアウトは未確定である。

## 3. 機能要件：イベント設定・記録

### FR-01 ハッシュタグの設定・引き継ぎ【確定】

利用者がイベントハッシュタグを設定・変更できる。設定した値は次の投稿に引き継ぎ、同一イベントで毎回再入力させない。現在の設定と保存済み投稿案の値を分離し、後からタグを変更しても過去の投稿案を書き換えない。複数タグの上限・入力形式は詳細設計で決める。

### FR-02 写真・動画の記録と取り込み【確定】

「記録する」からスマートフォンのカメラ／撮影UIを起動する。写真を撮影した場合は画像、動画を撮影した場合は動画として現在の投稿案へ取り込む。撮影キャンセル時に既存の本文・メディア・ハッシュタグを失わない。動画を初期版から一律に除外しない。

### FR-03 記録メディアの端末保存【確定】

記録した画像・動画は記録者の端末に保存し、LT Shareを終了しても残ること。保存先は写真ライブラリ／ギャラリーを基本とし、Xの添付UIから利用者が選択できること。通常のカメラアプリと同様に、撮影後の端末保存までを記録フローに含める。アプリ内プレビュー、一時メモリ、ブラウザ内キャッシュだけでは要件充足としない。

| 条件 | 求める動作 |
| --- | --- |
| 正常時 | 必要な権限と保存容量がある場合に保存する。アプリ終了後も写真／動画を端末で開け、Xから選択できる。 |
| 保存失敗時 | 権限拒否・容量不足・OSエラー等を利用者に知らせる。保存されていないものを「保存済み」と表示せず、再試行または退避の導線を用意する。 |
| Web固有の制約 | ダウンロード開始や共有シート表示だけを保存成功と判定しない。追加の保存操作が必要な方式は、カメラアプリ同等の要件を満たすかG-02で判断する。 |
| 削除との関係 | 「次の投稿へ」や下書きの整理によって、端末の写真ライブラリにある原本を自動削除しない。 |

### FR-04 メディアと投稿案の対応管理【補完】

撮影データ、生成文章、ハッシュタグを投稿案ごとに対応付ける。別の投稿へ移動した後で前のAI処理が完了しても、結果を新しい投稿案に混入させない。保存済みの原本と、解析用に縮小・抽出したデータを区別する。

**実現方式を先に検証する**: Webの撮影入力と写真ライブラリへの保存は同一機能ではない。Web方式でFR-03を満たせない場合、端末保存の要求を黙って緩和せず、ネイティブ機能を使う構成を検討する。[S-05]

## 4. 機能要件：AI文章生成・開発者の記載

### FR-05 利用者のChatGPT利用枠による文章生成【確定】

OpenAIの公式連携を用い、アプリ利用者自身のChatGPT利用枠で軽量モデルを実行する。運営者の秘密APIキーを配布しない。利用者に従量課金APIキーの作成・入力を求める方式、運営者課金API、端末内LLMへの代替は本要件に含めない。

Free・Plusでも利用しやすい低使用量を目標とする。ただし、Freeでの利用資格やPlusでの実行回数を保証するものではない。接続方式、対象プラン、利用可能モデル、画像／動画への対応はG-01の検証結果で確定する。[S-02][S-03][S-04]

### FR-06 文章の範囲・品質・文字数【確定＋補完】

| 項目 | 要件 |
| --- | --- |
| 長さ | 日本語100文字程度を目安とする。意味のない水増しや、厳密に100文字へ揃えることは求めない。 |
| 対象範囲 | 写真・録画など、利用可能な記録から分かる範囲を文章化する。LT全体を記録できていない場合は、その範囲を超えた要約をしない。 |
| 補完 | 省略された主語や接続表現を自然に整えることは許容する。判別できない人名、製品名、数値、成果、主張を事実として作らない。 |
| 情報不足 | 読み取り不能・情報不足の場合は、その状態を示す。推測だけの要約を生成せず、手入力または再記録へ進める。 |
| 投稿上限 | 要約、ハッシュタグ、任意の「開発者：」、改行等を含む本文全体をXの通常投稿上限に収める。要約を短くする必要がある場合は短縮し、タグを勝手に削らない。タグ等だけで上限を超える場合は修正を案内する。 |
| 使用量 | 不要な再生成、過去LT全文の毎回送信、無制限な自動再試行を避ける。入力データ量も含めて評価する。 |

Xの通常投稿は重み付き文字数で判定され、日本語の多くは2カウントとなる。表示上の「100文字」とX側の残り文字数を同一視しない。X上で追加されたメンション等の最終確認は利用者が行う。[S-07]

### FR-07 開発者ラベルの任意追加【確定】

「開発者をポストに含める」が有効な場合のみ、新規投稿本文に「開発者：」を追記する。無効な場合はラベルごと含めない。登壇者が不明なら、そのまま投稿へ進める。

アカウント検索、候補表示、登壇者事前登録をLT Share側には実装しない。必要な場合だけ利用者がX上で@入力・候補選択を行う。ラベル追加によってXの検索UIを自動起動することは要件に含めない。トグルの初期値・次の投稿での扱いはU-01に残す。

## 5. 機能要件：Xへの受け渡し・連続投稿

### FR-08 「ポスト確認」からXへ移動【確定】

「ポスト確認」でXの投稿用UIへ移動し、生成文・イベントハッシュタグ・任意の「開発者：」を入力済みで確認できること。Xアプリが利用できる環境ではアプリ側を優先し、利用できない場合はブラウザ版を利用する。最終的な投稿は利用者がX側で行う。

### FR-09 メディアの受け渡しと代替動作【条件付き】

対応環境では本文と画像／動画をまとめて共有する。本文とメディアの同時反映を確認できない環境では、本文をXに渡し、端末に保存済みのメディアを利用者が手動で添付する。自動添付の不成立を理由に撮影・端末保存を削除しない。

投稿用リンクやOSの共有機能を候補とし、G-03で方式を決定する。共有先としてXを選ぶ操作やXの共有用投稿画面を使う方式は検証候補とする。OS・X側の挙動を実機未確認のまま「常に直接起動・自動添付」と約束しない。[S-06]

### FR-10 「次の投稿へ」による保存と初期化【確定】

| 対象 | 操作後の状態 |
| --- | --- |
| 現在の投稿案 | 本文、当時のハッシュタグ、開発者トグル、メディア情報を端末内に保存する。未投稿のままでも保存できる。 |
| 新しい投稿案 | 現在のハッシュタグを引き継ぎ、本文と添付欄を初期化する。前回の文章やメディアを新規投稿へ混ぜない。 |
| 端末保存済みの原本 | そのまま残す。「次の投稿へ」による削除や移動は行わない。 |
| 保存の失敗 | 現在の内容を消して新規画面へ進めない。失敗を知らせ、元の投稿案を再保存できるようにする。 |
| 生成処理中 | 前の処理完了を必須の待ち条件にしない。処理結果は対応する投稿案へ反映し、OSによる処理中断時も再開／再試行できる状態を残す。 |

### FR-11 保存済み投稿案の再確認【確定＋補完】

前回の投稿案は端末内に残し、再確認できること。Xへの移動、共有キャンセル、「次の投稿へ」で消去しない。保存するのはLT Share内の投稿案であり、X上での修正後本文・追加メンション・投稿URL・投稿成否の自動同期は対象外とする。

**状態表示の禁止事項**: 「Xを開いた」「共有データを渡した」「次の投稿へ進んだ」だけで「投稿済み」と判定しない。共有機能の成功は、X上の投稿完了を意味しない。[S-06]

## 6. データ保存・管理要件

### 6.1 保存先と責任範囲

| データ | 保存先・方針 |
| --- | --- |
| 写真・動画の原本 | 利用者の端末の写真ライブラリ等。Xから添付できることをFR-03で検証する。本プロダクトのサーバーには保管しない。 |
| ハッシュタグ | 利用者の端末内。次の投稿、通常の再読み込み・再訪時に再利用できる形で保持する。 |
| 現在／過去の投稿案 | 利用者の端末内。本文、当時のタグ、開発者トグル、メディア情報、必要な処理状態を保持する。 |
| 解析用の中間データ | 可能な限り端末で処理する。モデル入力として必要な部分は、利用許可に基づきOpenAIへ送信する。 |
| 認証情報 | 独自会員情報・パスワード・秘密APIキーの永続保管は行わない。公式認証に必要なセッション管理は公式連携仕様に従う。 |
| X上の投稿 | Xの責任範囲。本プロダクトが同期・バックアップ・削除する機能は設けない。 |
| プラットフォームの保持 | SitesやOpenAI、OSのバックアップ等の保持方針は本プロダクトのDB有無と別に扱う。「外部に一切送信・保存されない」と表示しない。 |

### 6.2 投稿案が保持する論理情報

投稿案を区別する識別情報、作成・更新時刻、本文、ハッシュタグのスナップショット、開発者ラベルの有効状態、メディアの種別と対応情報、端末保存状態、文章生成状態を保持する。これは論理的な情報要件であり、DBテーブルや特定のフレームワークを指定するものではない。

### 6.3 復元・消去の扱い【補完】

通常の画面往復・再読み込みでは保存済みのハッシュタグと投稿案を復元する。一時的なプレビューURLだけを保存して、再訪時に内容を失う設計にしない。メディアへの再アクセスが許可されない場合は再選択を案内し、別の記録を誤って紐付けない。

ブラウザのサイトデータ削除、プライベートモード、容量制約等に対する無期限の保存・復旧は保証しない。ローカル保存は可能だが、保存禁止や容量超過で失敗する場合がある。[S-08]

投稿案の削除・保存件数・保存期間のUIはU-05で具体化する。下書きの削除と写真ライブラリの原本削除を連動させない。OSの写真同期・バックアップは利用者設定に依存する外部機能として扱う。

**明示的に作らないもの**: 履歴用サーバーDB、独自ログイン、秘密キー保管サービス、撮影データの自前クラウド保存、複数端末同期のためのバックエンドは初期構成に追加しない。

## 7. 非機能要件・異常時の動作

本章は、合意済みの体験を安全に成立させるための補完要件である。秒数・容量・対応バージョンなど、未計測の性能値は保証値として固定しない。

| ID | 区分 | 要件 |
| --- | --- | --- |
| NFR-01 | 操作性 | 記録と次の投稿への移動を中心に設計する。登壇者検索を必須化しない。処理中は状態を示し、多重タップで同じ保存・生成・共有を重複実行しない。 |
| NFR-02 | データ保全 | 保存が完了する前に元の投稿案を消さない。外部アプリへの移動・共有キャンセル・AI失敗で、保存済みのデータを失わない。 |
| NFR-03 | 利用量 | 軽量モデルを利用し、無制限な再試行や不要な全履歴送信を避ける。上限到達時に運営者APIや有料クレジットへ無断で切り替えない。 |
| NFR-04 | セキュリティ | 秘密APIキーの埋め込みやChatGPT／Xのセッション情報の抜き出しを行わない。認証情報を独自の投稿履歴・診断ログへ保存しない。 |
| NFR-05 | プライバシー | 撮影、SNS公開、OpenAIでの処理を区別して案内する。本文生成のために送信する内容と保存先を説明し、必要最小限のデータを扱う。 |
| NFR-06 | AIの扱い | 画像・動画内の文言は解析対象データとして扱い、アプリの操作指示として実行しない。事実にない断定を避け、最終投稿前に人が確認できる。 |
| NFR-07 | 対応環境 | 実機で検証したOS・ブラウザ・Xアプリ版を対応表へ記録する。PCブラウザのみの検証結果をスマートフォンの動作保証に流用しない。 |

### 7.1 異常時の最低限の動作

| 状況 | 動作 |
| --- | --- |
| カメラ／保存権限の拒否 | 何が利用できないかを示し、許可の再設定を案内する。既存の投稿案は保持する。 |

## 8. 外部依存・先行検証

以下は仕様上の前提を満たせるか確認するための検証であり、本書作成時点では実機検証・接続検証とも未実施である。公開ドキュメントの確認と、対象環境での動作確認を区別する。

### G-01 Sites × 利用者のChatGPT利用枠

Sites上の対象公開形態で、独自バックエンドや秘密キー保管を作らずに、利用者自身の枠で画像から文章生成できるか確認する。公式の許可フロー、対象プラン、モデル、認証状態の扱い、利用枠消費、失敗時の動作まで確認する。

公式資料では、Sitesの本人確認とChatGPT利用枠の利用許可は別の仕組みとして扱われている。商用アプリ向け利用枠はGo・Plus・Proが対象とされ、オープンソースの公開フローとは条件が異なる。有料・リモートホスト型アプリは提供条件の確認が必要である。[S-01][S-02][S-03]

公開されている利用枠連携フローでは、対応モデルへの画像入力は可能だが、音声・動画の直接入力と文字起こしAPIは未対応とされる。Sitesで採用できる方式にその制約が適用されるかを確認する。動画から静止画を抽出する案は候補であり、発言の要約までできるとみなさない。[S-04]

### G-02 Webでの写真・動画の端末保存

写真と動画をそれぞれ記録し、写真ライブラリ等に残り、Xで選べることを確認する。保存後のアプリ終了、保存権限拒否、容量不足、縦横の向き、対応形式を確認する。撮影入力だけでは永続保存を保証できないため、撮影とは別に保存の完了条件を確立する。[S-05]

合格条件はFR-03を満たすこと。保存操作の追加が必要なWeb方式しか成立しない場合は、その操作負担を明示して要件適合性を判断する。未承認の手動保存を「自動保存できた」と扱わない。

### G-03 Xへの本文・メディア受け渡し

Xアプリあり／なし、写真／動画、共有キャンセル、X未ログインを組み合わせて確認する。本文、タグ、開発者ラベルが正しく入り、メディアが自動添付されるかを検証する。Web Shareは共有データの一部が省略される場合があるため、呼び出し成功だけで同時反映を保証しない。[S-06]

**検証結果に応じた判断**: G-01不成立：AIの前提を満たす公式方式を再調査し、別課金・独自バックエンドへ無断変更しない。G-02不成立：保存要件を維持してネイティブ機能利用を検討する。G-03で自動添付不成立：合意済みの「端末保存＋Xで手動添付」を採用できる。本文の自動入力まで不成立なら別途判断する。

検証対象候補：iPhoneのSafari、AndroidのChrome、Sitesを開くアプリ内ブラウザ。正式な対応OS・バージョンはU-02で決める。X投稿用リンクの具体的なURL・パラメータは本書で固定せず、最新仕様と実機で確認する。
