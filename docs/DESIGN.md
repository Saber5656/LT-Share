# LT Share on X 画面設計（モック）

- 対象: [要件定義書 LT-SRS-001 v1.0](requirements.md) の画面モック
- 作成日: 2026-10-09
- 状態: **クリック可能な画面モックのみ**。カメラ・端末保存・ChatGPT連携・Xへの受け渡しは実装しておらず、タイマーと同梱写真で再現している。実機動作・Sites公開は未実施。

## 1. 設計の進め方と選定

OpenAI の Product Design plugin（0.1.56）の手順に沿って進めた。

1. **get-context**: 対象＝LT参加者向けのスマホWeb（OpenAI Sites 前提）。基準サイズ 390 x 844、日本語UI。主動線＝ハッシュタグ設定 → 記録 → AI文章 → 開発者トグル → ポスト確認 → 次の投稿へ。
2. **ideate**: 方向性の異なる3案を画像生成（Codex built-in image_gen）。生成順＝表示順。
   | 表示番号 | ファイル | 方向性 |
   | --- | --- | --- |
   | 1 | [venue-dark-capture.png](design/concepts/venue-dark-capture.png) | 暗い会場向け、カメラ中心 |
   | 2 | [post-preview-composer.png](design/concepts/post-preview-composer.png) | 投稿内容のプレビューを中心にした白基調 |
   | 3 | [event-session-timeline.png](design/concepts/event-session-timeline.png) | 1晩のLTを縦に並べるセッション型 |
3. **選定**: プロダクトオーナーが **案2** を選択。フィードバック:「ハッシュタグはひとつとは限らないから複数選択できるように、もう少しフォーム入力形式感があった方が手順通りに進めるかも」。
4. **修正案**: 案2の見た目を保ち、①ハッシュタグ（複数）②記録 ③投稿文 ④開発者 の番号付きフォームに再構成 → [post-preview-form-revised.png](design/concepts/post-preview-form-revised.png)。**これを実装の正とした。**
5. **image-to-code**: plugin の `mobile-app` テンプレート（Sites 向けビルド出力つき）で `mock/` に実装。
6. **design-qa**: 修正案と実画面を並べて比較し、P0〜P2を解消して passed。記録は [mock/design-qa.md](../mock/design-qa.md)。

プロンプトと生成元の対応は [concepts/manifest.json](design/concepts/manifest.json)・[manifest-revision.json](design/concepts/manifest-revision.json) に残している。

## 4. モックで再現しているもの / していないもの

| 機能 | モックの挙動 |
| --- | --- |
| カメラ | 同梱写真をファインダーに表示。撮影すると、その投稿案番号に対応する写真を取り込む。動画は録画した秒数を表示するが、中身は同じ写真 |
| 端末保存 | 0.9秒後に「保存済み」。モック操作で次の1回を失敗させられる |
| ChatGPTでの生成 | 1.8秒後に投稿案番号に対応する定型文を表示。モック操作で次の1回を失敗/利用上限にできる |
| Xへの受け渡し | 「Xで開く」でトーストを出し、状態を「Xで開いた」にするだけ。Xは開かない |
| 投稿案の保存 | 画面のメモリ上のみ。再読み込みで初期状態に戻る |
| 遅れて届いた生成結果 | 生成中に「次の投稿へ」を押しても、結果は元の投稿案に入る（FR-04） |

「モック操作」は「保存した投稿案」画面の下部にあり、実アプリには含めない。初回の案内画面もモックではここから開く（モックは主画面から始まる）。

画面の文言（「この端末に保存した投稿案です」など）は実アプリの挙動を前提にしている。モック自体は端末に保存しない。

画面状態の再撮影は `cd mock && MOCK_URL=<開発サーバーのURL> npm run qa:capture`（出力は `mock/test-results/qa/`）。

## 2026-10-19 単独Webへ復帰

ChatGPT内アプリの操作負担が大きいという実利用フィードバックを受け、単独Webの4段フォームを主経路へ戻す。Product Design 0.1.56 のuser-context preflightを実施し、選定済み `post-preview-form-revised.png` と既存 `app/` を再利用する。別チャットの開始、@選択、会話からの結果コピーは要求しない。

- 写真を取り込むと、その場でAI文章生成を開始する。写真保存の確認を生成開始の必須条件にしない。
- 本文は常に編集可能。生成中の手入力と、次の投稿へ進んだ後の遅延結果を保全する。
- 初回に「写真の内容をAIへ送って投稿文を作る」設定を明示し、後から切替可能。未設定/利用上限時は理由を示し、写真・本文を保持する。
- 写真の原本と投稿案は従来どおり端末内。AIへの送信用コピーだけ縮小し、独自サーバーへの保存はしない。
- 動画は記録・保存を維持する。自動要約は抽出した静止画に基づく場合、その範囲を表示する。音声を聞いたと偽らない。
- AIキーは運営側のSites秘密設定。利用者にキー発行や外部チャット操作を要求しない。APIへの中継のみステートレスで追加し、履歴DBは作らない。
- 公開範囲は引き続き本人限定。無料プラン確認とキー設定が済むまでは生成を有効と表示せず、有料APIへ切り替えない。
# 2026-10-20：端末内AIの準備と生成

既存の選定画像 `design/concepts/post-preview-form-revised.png` と白黒4段フォームを視覚的ターゲットとして継続する。Product Design 0.1.56のuser-context preflight、get-context、image-to-codeを適用。対象はスマートフォン向け単独Web、目的は会話やAPIキー入力を挟まず写真から投稿文を作ること。

記録欄の既存自動生成設定を「端末内AI」へ変更。未準備では約0.9GB・Wi-Fi推奨・写真を送信しない説明と「端末内AIを準備」の1ボタン。準備中は進捗と中止を表示し、手入力・記録・タグ編集を続けられる。準備済みでは自動生成トグルと再生成。生成中は中止、失敗・非対応は理由と手入力を案内する。別画面/外部ログイン/モデル選択UIを増やさない。

既存の字体、Phosphorアイコン、余白、44px操作領域、本文編集、下書き保護を維持する。準備失敗と画像読み取り失敗は区別する。自動ダウンロード・クラウドへの自動切替は行わない。初回の準備開始は利用者の操作に限定する。物理スマホの性能確認前は試験機能と明記する。

### 2026-10-20 画面確認結果

Chromeの実画面で準備操作後に「準備ができました」を確認。390px幅でもタグ→記録→端末内AI→投稿文→任意開発者という順序、既存のモノクロ配色と区切りを維持し、横スクロールや文字の重なりを生じない。今回の参照は既存フォームの階層・余白・操作導線であり、写真未選択の状態と参照画像の写真選択済み状態を同一の画像一致と評価していない。全ページスクリーンショットでは固定フッターが途中に写るため、画面操作によるスクロールも併せて確認する。スマホ幅のChrome表示は物理スマホでの検証を代替しない。

### 2026-10-20 サーバー要約への変更（利用者指定）

モデル取得待ちで聴講を妨げるため、ローカルAIの準備ボタン・容量説明・進捗を削除する。既存フォームは保持し、記録の直下に「写真から自動で投稿文をつくる」と送信先の短い説明、生成中の中止、失敗時の再試行を置く。写真を選ぶだけで始まることを優先し、別のChatGPT会話やモデル選択画面は作らない。配色・見出し・44px操作領域は既存承認画像を継承。Product Design image-to-code手順で既存ターゲットを参照して変更範囲を確認する。

### 2026-10-20 写真ライブラリからの取り込み

既存の番号付きフォームと撮影ボタンを維持する。「記録」欄のプレビュー直下に全幅の「写真・動画を選ぶ」を追加し、PhosphorのImagesアイコンと既存outline-buttonを利用する。撮影の写真/動画切替とは独立した、capture属性のない画像・動画共通の選択入口とする。ヘッダーには追加の操作を詰め込まない。

取り込んだメディアは既存のプレビュー・端末内保持・サーバー要約・投稿案に接続する。原本が端末にあることを利用者が確認すれば、共有経由の再保存を求めず先へ進める。OSが選択UI内で撮影を許す場合もあるため、取り込みだけを端末保存完了とはみなさない。置き換え前の確認は選択先を保持し、キャンセル時は元の投稿案を維持する。Product Designの既存画面比較とスマホ幅の操作確認で評価する。

### 2026-10-20 実利用フィードバック対応

添付の投稿確認画面と暗転したOSカメラ画面を確認。Product Designの既存フォーム/カメラ設計を継承し、主動線を短くする。投稿文の順は感想本文→任意の開発者ラベル→末尾ハッシュタグ。端末の原本保存確認を廃止し、保存操作は任意とする。アプリ内のメディアと投稿案の自動保存・保存失敗時の保全は維持。開発者トグルは次の投稿に引き継ぐ。

カメラは既存OS撮影入力からgetUserMediaのアプリ内プレビューへ切り替える。黒背景に実際の映像、上に閉じる/種別、下に撮影または録画停止、カメラ切替。既存Phosphorアイコンを利用する。準備中・権限拒否・映像未到達・録画非対応を表示し、再試行と写真ライブラリへ進める。映像が到達する前に撮影を有効にしない。終了・画面非表示・切替時にストリームを停止し、二重占有を防ぐ。写真アプリへの自動追加成功とは表示しない。

文章は読めた製品名/機能→具体的な利用場面→「便利そう」「面白い」等の自然な所感。未体験の使用実績や読み取れない固有名詞を作らない。動画は約5秒間隔、長尺は全体から最大12フレームを選び、時系列の一覧画像にして1回の推論へ渡す。音声は解析しない。

### 2026-10-20 写真付きXハンドオフの優先

Product Design auditを適用。既存のポスト確認シートは本文専用リンクが主ボタン、写真付き共有は下部の副操作になっており、主操作だけでは写真が渡らなかった。既存モノクロ配色・写真プレビュー・本文表示を維持し、メディアがあるときだけ「写真/動画と本文をXへ」を主操作とする。「次の共有画面でXを選んでください」を直下に表示し、本文のみのリンクを明示的な副操作へ下げる。別画面や設定は追加しない。

準備中・データなし・共有不可では写真付き主操作を無効化する。キャンセル・失敗を同じシートに表示し、本文のみへ自動遷移しない。OS共有先の選択やXでの最終確認は利用者が行う。画面テストの共有APIは代替実装であり、実機Xが両方を受け取った証拠ではない。

### 2026-10-20 実機確認後の共有画面の簡素化

利用者が写真と本文のX投稿確認への同時反映を報告。今回提供された2枚の画面をProduct Design auditの根拠にした。ブラウザ保存の常時バナーが投稿準備より目立ち、写真付き共有の下に本文専用リンク2種とコピーが並ぶため、主操作へ集中させる。

ブラウザ保存の成功/失敗・保存不可/スキップの常時通知を取り除く。別タブで編集できない理由と再読み込みは維持する。保存機構や原本・履歴は削除せず、次の投稿へ移る際の実保存失敗は本文を保持したまま再試行できる。

メディアがある場合は写真/動画付き共有を主操作とし、本文専用リンクとコピーは『共有できない場合』の折りたたみにまとめる。媒体が欠落・読込エラー・共有非対応、または共有失敗/結果不明時は補助操作を展開する。キャンセルは失敗と扱わない。メディアなしの本文共有は変更しない。Web Shareの共有先X選択を自動化したとは表示しない。標準details/summaryのキーボード操作、44px操作領域、既存白黒の見た目を維持する。
