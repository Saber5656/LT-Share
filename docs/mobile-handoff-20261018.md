# スマホからのX受け渡し修正

## 目的と設計判断

実機から「Xで開く」が未ログインのWeb版へ進むという報告を受けた。現行の白基調・番号付きフォーム・ポスト確認シートを維持する。Product Designのindex/user-context/auditを参照し、preflightを実施。新しい画面や配色は作らない。

変更前の実画面をChromeで確認した。主ボタンはHTTPSの投稿用リンクのみで、アプリ向けの明示的な起動リンク・本文コピー・Web版の選択肢がない。内蔵ブラウザは利用不可だったため、利用可能なChromeで確認した。

採用する修正：スマホは主ボタンを「Xアプリで開く」とし、タップから直接アプリ向けリンクへ進む。補助操作として「ブラウザ版で開く」「本文をコピー」をシート内に置く。デスクトップは従来のWebリンクを主操作にする。コピー失敗時は手動選択を案内する。起動要求だけを実際の起動・投稿成功と表示しない。

iOSでは従来のtwitterスキーム、AndroidではChromeのパッケージ指定Intentを利用する。これは実機検証が必要な接続候補であり、現行Xアプリ全版の対応保証ではない。自動タイマーで別画面に飛ばす処理は作らない。

## 検証範囲

リンク本文の符号化、iPhone/iPad/Android/desktopの振り分け、本文コピーの成功・拒否、投稿上限と既存履歴保存をテストする。ブラウザ上の確認ではOSによるアプリ起動までは証明できない。実機では同じSiteから本文・タグが入ったXアプリの投稿画面へ移るかを確認する。

## 今回の残りの要求

- 写真・動画を共有シートを介さず写真アプリへ保存：現行Webでは未実装。PhotoKit等の端末側機能が必要。Sites版を残しつつ端末アプリを追加するか利用者へ確認中。
- 本人のChatGPT枠によるAI要約：接続仕様・ホスト型アプリの利用条件が未確認。申請準備は`siwc-hosted-request.md`。別課金APIや端末内モデルへ無断で切り替えない。

参照：[Chrome Android Intent](https://developer.chrome.com/docs/android/intents)、[HTML Media Capture](https://www.w3.org/TR/html-media-capture/)、[Apple Photos保存例](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-on-ios)。

## 確認結果

- 変更前：ポスト確認シートをChromeで操作し、WebリンクのみであることをDOM・実画面から確認。
- 変更後：iPhone/Androidを想定した画面でアプリ向け主操作、Web版、コピーの3つが表示される。代表画像は[修正後のポスト確認](design/screenshots/20261018-x-app-handoff.png)。元のフォーム・本文プレビュー・文字数・閉じる操作を維持。新規の補助リンクに色を明示して、ブラウザの既読リンク色が出る問題を修正した。
- 画面操作：タップ要求後の表示、コピー成功と拒否時の案内、下書き・タグの再読み込み後保持を確認。unit107件、全E2E27件が成功。独立レビューの指摘（モバイルでタップ後の確認不足）を採用し、追加後に該当2件も成功。
- 画面キャプチャ：初回はシートの表示アニメーション途中だったため不採用。アニメーション終了状態を撮り直し、文字・枠・各ボタンが読める画像を採用した。
- 未確認：実機のXアプリ起動、Xアプリ内に反映される本文、実機写真アプリへの直接保存、本人利用枠のAI実行。これらをブラウザ試験の成功から推定しない。
